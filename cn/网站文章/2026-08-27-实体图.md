实体消歧（Entity Disambiguation）是一种让 AI 引擎把你在不同平台、不同页面里的身份信息拼成同一个实体的结构化数据写法。AI 引擎（秘塔、Kimi、豆包、Perplexity）在回答"纪优是谁"时，不会只读你自建站的关于页——它从知乎主页、GitHub 资料、文章页的作者字段里各取一块，尝试拼图。如果这些碎片的身份标识对不上，AI 会把它们当成几个不同的人。实体图用三个东西解决这个问题：`@id` 唯一标识符、`sameAs` 多平台锚点、`knowsAbout` 稳定知识领域。

本文记录一次真实的代码改造：把一个自建站的 JSON-LD 从"每页重复内联作者对象"升级为"用 `@id` 串起来的实体图"。改造对象是一个 Node.js 构建脚本（`build.js`），它把 Markdown 文章转成 HTML，并自动生成 JSON-LD。

## 为什么 AI 引擎需要实体消歧？

AI 引擎生成回答时，会从多个来源综合信息。你的身份信息散落在至少四个地方：自建站首页、自建站文章页的作者字段、知乎主页、GitHub 资料。如果每个地方的 JSON-LD 都把作者写成一个独立的内联对象，AI 看到的是四组字段相似但无法确认是否指向同一个人的数据。

传统写法（每页内联一份作者对象）的问题在于：每个 Person 对象都是孤立的，AI 没有"这是同一个人"的硬证据。它只能靠名字字符串匹配——但叫"纪优"的人可能不止一个。实体消歧的核心是给实体一个全局唯一的 `@id`，让 AI 跨页面、跨数据源时能确认"这个 `@id` 指向的是同一个人"。

Schema.org 的实体消歧机制依赖三个字段配合工作。`@id` 是实体的唯一身份证号，用稳定 URL 形式（如 `https://www.jiyou.site/#person`）。`sameAs` 声明这个实体在其他平台的对应身份，是跨平台拼图的锚点。`knowsAbout` 声明实体的稳定专业领域，帮 AI 判断这个人在什么话题上有发言权。三者配合，AI 引擎才能把散落的身份碎片拼成一张完整的实体图。

## 改造前：每页重复内联的孤立对象

改造前，构建脚本为每篇文章生成两个 JSON-LD 块：一个 Article，一个 Person。Person 是直接内联在每篇文章页里的，每次都重新写一遍所有字段。

```javascript
const articleJsonLd = JSON.stringify({
  '@context': 'https://schema.org',
  '@type': 'Article',
  headline: article.title,
  description: article.description || '',
  // 改造前：author 是一个完整的内联对象，每篇文章都重复定义
  author: { '@type': 'Person', name: AUTHOR_NAME, url: AUTHOR_URL },
  publisher: { '@type': 'Organization', name: AUTHOR_NAME, url: AUTHOR_URL },
  datePublished: article.date,
  dateModified: article.date,
  inLanguage: 'zh-CN',
  mainEntityOfPage: `${SITE_URL}/articles/${article.slug}.html`,
}, null, 2);

const personJsonLd = JSON.stringify({
  '@context': 'https://schema.org',
  '@type': 'Person',
  name: AUTHOR_NAME,
  url: AUTHOR_URL,
  description: 'AI 智能体应用与生成式引擎优化（GEO）研究者',
  sameAs: [AUTHOR_SAMEAS],   // Bug：AUTHOR_SAMEAS 已是数组，再包一层变成嵌套数组
  knowsAbout: article.tags || [],  // 问题：知识领域随每篇文章的 tag 变动
}, null, 2);
```

这段代码有两个问题。第一个是 `sameAs: [AUTHOR_SAMEAS]`——当 `AUTHOR_SAMEAS` 是字符串时它能工作，但把 `AUTHOR_SAMEAS` 改成数组后，`[AUTHOR_SAMEAS]` 就变成了嵌套数组 `[[...]]`，这不是合法的 sameAs 用法。第二个是 `knowsAbout: article.tags || []`——知识领域跟着每篇文章的 tag 变，讲 GEO 的文章说"我知道 GEO"，讲段落写作的文章说"我知道自足段落"，AI 拼不出一个稳定的"纪优研究什么"的画像。

首页的 WebSite JSON-LD 也有同样的问题，而且因为首页是手写模板字符串（不是 `JSON.stringify` 生成），`sameAs` 直接写成了 `"${AUTHOR_SAMEAS}"`——数组被模板化成了一个逗号字符串，JSON 里是 `"https://...,https://..."`，既不是合法的 URL 数组，也不是合法的 sameAs 声明。

```javascript
// 首页手写模板里的 Bug 写法
"sameAs": ["${AUTHOR_SAMEAS}"]   // 数组被 toString 成 "a,b"，再塞进单元素数组
```

## 改造第一步：集中管理实体配置

改造的第一步是把所有实体相关的配置集中到一个常量区，让全站的实体定义只在一处维护。这样改一次 `sameAs`，全站的文章页和首页同时生效，不会出现"文章页的 sameAs 改了但首页忘了改"的脱节。

```javascript
// ── 配置 ──
const SITE_URL = 'https://www.jiyou.site';
const AUTHOR_NAME = '纪优';
const AUTHOR_URL = SITE_URL;
const AUTHOR_DESCRIPTION = 'AI 智能体应用与生成式引擎优化（GEO）研究者';

// 实体 sameAs 锚点（跨平台身份验证，只填真实拥有的平台）
const AUTHOR_SAMEAS = [
  'https://www.zhihu.com/people/yeah-98-35',   // 知乎（实体锚点）
  'https://github.com/jaykaai',                  // GitHub（代码实体锚点）
];

// 稳定知识领域（knowsAbout，不随文章 tag 变动）
const AUTHOR_KNOWS_ABOUT = [
  '生成式引擎优化',
  'AI 智能体应用',
  '结构化数据',
  '搜索引擎优化',
];

// 实体图 @id（实体消歧用，AI 引擎靠 @id 拼合同一个实体）
const PERSON_ID = `${SITE_URL}/#person`;
const ORG_ID = `${SITE_URL}/#organization`;
const WEBSITE_ID = `${SITE_URL}/#website`;
```

这段配置有三个要点。`AUTHOR_SAMEAS` 是数组，只填真实拥有的平台账号——知乎和 GitHub。sameAs 不是越多越好，填一个打不开的页面比不填更糟，因为 AI 去验证时拿到 404 会降低这个实体的可信度。`AUTHOR_KNOWS_ABOUT` 是作者作为一个研究者的稳定身份，不随每篇文章的主题变动——无论这篇讲 GEO 还是讲段落写作，"纪优"研究的都是这四个领域。三个 `@id` 常量用稳定 URL 形式，这是 Schema.org 实体消歧的标准做法：`@id` 必须是一个全局唯一的 URI，用自己域名下的片段标识符（`#person`）是最稳定的方式。

## 改造第二步：文章页用 @id 串起实体图

第二步改文章页的 JSON-LD 生成。核心变化是：Article 的 `author` 和 `publisher` 不再内联完整对象，改成用 `{"@id": ...}` 引用实体图里已有的 Person 和 Organization。同时新增一个独立的 Organization 块，让 Person 和 Organization 互相引用。

```javascript
function renderArticle(article, topicCount) {
  let htmlBody = marked.parse(article.body);
  htmlBody = processAnnotations(htmlBody);

  // Article 块：author/publisher 用 @id 引用，不重复定义实体
  const articleJsonLd = JSON.stringify({
    '@context': 'https://schema.org',
    '@id': `${SITE_URL}/articles/${article.slug}.html#article`,
    '@type': 'Article',
    headline: article.title,
    description: article.description || '',
    author: { '@id': PERSON_ID },        // 引用实体图，不重复定义
    publisher: { '@id': ORG_ID },
    datePublished: article.date,
    dateModified: article.date,
    inLanguage: 'zh-CN',
    mainEntityOfPage: `${SITE_URL}/articles/${article.slug}.html`,
  }, null, 2);

  // Person 块：实体图的中心，带 @id + sameAs + knowsAbout + worksFor
  const personJsonLd = JSON.stringify({
    '@context': 'https://schema.org',
    '@id': PERSON_ID,
    '@type': 'Person',
    name: AUTHOR_NAME,
    url: AUTHOR_URL,
    description: AUTHOR_DESCRIPTION,
    sameAs: AUTHOR_SAMEAS,               // 直接用数组，不要再包一层
    knowsAbout: AUTHOR_KNOWS_ABOUT,     // 稳定知识领域，不用 article.tags
    worksFor: { '@id': ORG_ID },        // 指向 Organization
  }, null, 2);

  // Organization 块：和 Person 互相引用
  const orgJsonLd = JSON.stringify({
    '@context': 'https://schema.org',
    '@id': ORG_ID,
    '@type': 'Organization',
    name: AUTHOR_NAME,
    url: AUTHOR_URL,
    description: AUTHOR_DESCRIPTION,
    sameAs: AUTHOR_SAMEAS,
    founder: { '@id': PERSON_ID },      // 指回 Person，闭环
  }, null, 2);

  const faqJsonLd = generateFaqJsonLd(article.faq, htmlBody);

  return `<!DOCTYPE html>
<html lang="zh-CN">
<head>
  ...
  <script type="application/ld+json">
${articleJsonLd}
  </script>
  <script type="application/ld+json">
${personJsonLd}
  </script>
  <script type="application/ld+json">
${orgJsonLd}
  </script>
  ${faqJsonLd ? `<script type="application/ld+json">\n${faqJsonLd}\n  </script>` : ''}
</head>
```

三个要点。Article 块的 `author: { '@id': PERSON_ID }` 是引用，不是定义——它告诉 AI"这篇文章的作者是 `#person` 那个实体"，实体本身的完整定义在下面的 Person 块里。Person 和 Organization 互相用 `worksFor` 和 `founder` 指向对方，形成闭环——Person 为 Organization 工作，Organization 的创始人是 Person。`sameAs: AUTHOR_SAMEAS` 直接用数组常量，不再包 `[]`，这修掉了改造前的嵌套数组 Bug。

构建后生成的 HTML 里，每篇文章页的 `<head>` 现在有三个独立的 `<script type="application/ld+json">` 块（Article、Person、Organization），它们靠 `@id` 互相串联：

```json
{
  "@context": "https://schema.org",
  "@id": "https://www.jiyou.site/articles/zi-zu-duan-luo.html#article",
  "@type": "Article",
  "headline": "GEO 写作的核心方法：自足段落与答案优先",
  "author": { "@id": "https://www.jiyou.site/#person" },
  "publisher": { "@id": "https://www.jiyou.site/#organization" }
}
```

```json
{
  "@context": "https://schema.org",
  "@id": "https://www.jiyou.site/#person",
  "@type": "Person",
  "name": "纪优",
  "url": "https://www.jiyou.site",
  "sameAs": [
    "https://www.zhihu.com/people/yeah-98-35",
    "https://github.com/jaykaai"
  ],
  "knowsAbout": ["生成式引擎优化", "AI 智能体应用", "结构化数据", "搜索引擎优化"],
  "worksFor": { "@id": "https://www.jiyou.site/#organization" }
}
```

## 改造第三步：首页 WebSite 加入实体图

第三步改首页。首页的 JSON-LD 是手写模板字符串（不走 `JSON.stringify`），所以不能直接放 JS 数组进去，要用 `JSON.stringify()` 把数组转成合法的 JSON 文本再插值。这一步也新增了独立的 Person 和 Organization 块——之前首页只有一个 WebSite 块，作者信息内联在里面，现在拆出来用 `@id` 引用。

```javascript
  <script type="application/ld+json">
  {
    "@context": "https://schema.org",
    "@id": "${WEBSITE_ID}",
    "@type": "WebSite",
    "name": "${AUTHOR_NAME}",
    "url": "${SITE_URL}/",
    "description": "AI 智能体应用与生成式引擎优化（GEO）研究",
    "author": { "@id": "${PERSON_ID}" },
    "publisher": { "@id": "${ORG_ID}" },
    "inLanguage": "zh-CN"
  }
  </script>
  <script type="application/ld+json">
  {
    "@context": "https://schema.org",
    "@id": "${PERSON_ID}",
    "@type": "Person",
    "name": "${AUTHOR_NAME}",
    "url": "${AUTHOR_URL}",
    "description": "${AUTHOR_DESCRIPTION}",
    "sameAs": ${JSON.stringify(AUTHOR_SAMEAS)},
    "knowsAbout": ${JSON.stringify(AUTHOR_KNOWS_ABOUT)},
    "worksFor": { "@id": "${ORG_ID}" }
  }
  </script>
  <script type="application/ld+json">
  {
    "@context": "https://schema.org",
    "@id": "${ORG_ID}",
    "@type": "Organization",
    "name": "${AUTHOR_NAME}",
    "url": "${AUTHOR_URL}",
    "description": "${AUTHOR_DESCRIPTION}",
    "sameAs": ${JSON.stringify(AUTHOR_SAMEAS)},
    "founder": { "@id": "${PERSON_ID}" }
  }
  </script>
```

手写模板里插值数组最容易踩的坑就是 `"${AUTHOR_SAMEAS}"`。JS 数组被模板字符串隐式 `toString()` 后变成 `"https://...,https://..."`，塞进 JSON 后是一个带逗号的字符串，既不是 URL 也不是合法的 sameAs 数组。正确做法是 `${JSON.stringify(AUTHOR_SAMEAS)}`，它输出的是 `["https://...","https://..."]` 这样的合法 JSON 数组文本，直接嵌进 JSON 对象里语法正确。这是改造前首页的核心 Bug，改造后用 `JSON.stringify` 一次性修掉。

## 改造第四步：验证实体图闭环

改造完要验证三件事：所有 JSON-LD 块语法合法、`@id` 引用形成闭环、sameAs 和 knowsAbout 内容正确。语法验证用 Node.js 解析每个 `<script type="application/ld+json">` 块：

```javascript
const fs = require('fs');
const re = /type="application\/ld\+json">\s*([\s\S]*?)<\/script>/g;
['site/articles/zi-zu-duan-luo.html', 'site/index.html'].forEach(f => {
  const h = fs.readFileSync(f, 'utf8');
  let i = 0, m;
  console.log('=== ' + f + ' ===');
  while ((m = re.exec(h))) {
    i++;
    try { JSON.parse(m[1]); console.log('  块' + i + ': ✅ 合法'); }
    catch (e) { console.log('  块' + i + ': ❌ ' + e.message); }
  }
});
```

验证结果：文章页 4 块（Article + Person + Organization + FAQPage）全部合法，首页 3 块（WebSite + Person + Organization）全部合法。`@id` 引用闭环用 grep 确认：Article 的 author 指向 `#person`，Person 的 worksFor 指向 `#organization`，Organization 的 founder 指回 `#person`，WebSite 的 author 和 publisher 分别指向 `#person` 和 `#organization`。实体图闭环成立。

## 实体图的完整结构

改造完成后，整站的实体图结构如下。四个实体通过 `@id` 互相引用，AI 引擎无论从哪个页面进入，都能沿着 `@id` 找到完整的实体定义。

```text
Article (#article)              WebSite (#website)
  ├─ author → #person             ├─ author → #person
  └─ publisher → #organization   └─ publisher → #organization
        ↑                               ↑
        └──────────┬───────────────────┘
                   │
Person (#person) ←┼→ worksFor / founder ←→ Organization (#organization)
  ├─ sameAs: [知乎, GitHub]              ├─ sameAs: [知乎, GitHub]
  └─ knowsAbout: 4 个稳定领域            └─ founder → #person
```

实体图的关键不是每个页面有多少 JSON-LD 块，而是这些块之间能不能通过 `@id` 连起来。AI 引擎读到你文章页的 `author: {"@id": ".../#person"}` 时，它会去找 `#person` 这个 `@id` 的完整定义。在文章页它能在同页的 Person 块里找到；在首页它也能在首页的 Person 块里找到——两个页面指向的是同一个 `@id`，AI 据此确认这是同一个人。再顺着 `sameAs` 去知乎和 GitHub 验证，"纪优"这个实体的身份就跨平台闭环了。

## 为什么 sameAs 只填真实拥有的平台？

sameAs 是实体消歧的锚点，它告诉 AI"我在这个平台的身份是 X"。AI 引擎会去这些 URL 验证身份是否一致。填一个你确实拥有、且资料与自建站一致的页面，是一次成功的身份验证，增加实体可信度。填一个打不开的、或资料对不上的页面，是一次失败的身份验证，反而稀释可信度。

sameAs 不是社交链接列表，是身份验证锚点。填之前问自己：这个 URL 我能打开吗？这个页面上的人和我自建站说的是同一个人吗？两个问题都是"是"才填进去。知乎主页和 GitHub 主页是两个天然适合做 sameAs 的平台——知乎是国内 AI 引擎能抓取的中文身份平台，GitHub 是全球通用的代码贡献者身份平台，两者覆盖了中文和英文两个圈层的身份验证。

## 为什么 knowsAbout 不用文章 tag？

knowsAbout 声明的是"纪优作为一个研究者，稳定研究哪些领域"，不是"这篇文章讲了什么"。如果 knowsAbout 跟着文章 tag 走，讲 GEO 的文章说你知道"GEO"，讲段落写作的文章说你知道"自足段落"——AI 拼不出一个稳定的身份画像，只看到一堆零散的话题标签。

稳定的 4 个领域（生成式引擎优化、AI 智能体应用、结构化数据、搜索引擎优化）是"纪优"这个实体的专业边界。无论写什么文章，这个边界不变。AI 引擎在判断"纪优在 GEO 话题上有没有发言权"时，看到的是一份稳定的、跨文章一致的专业声明，而不是随着每篇文章波动的标签集合。这是实体可信度的一部分：一个研究边界稳定的人，比一个每篇文章都在变话题的人，更值得被 AI 当作可引用的来源。

## 三个字段怎么配合工作？

实体消歧的三个字段各司其职，缺一不可。`@id` 解决"这是不是同一个实体"的问题——全局唯一标识，让 AI 跨页面跨平台时能确认指向同一个人。`sameAs` 解决"这个实体在其他平台是谁"的问题——多平台身份锚点，让 AI 能去知乎和 GitHub 验证身份。`knowsAbout` 解决"这个实体在什么话题上有发言权"的问题——稳定专业边界，让 AI 判断是否值得引用这个人的观点。

三个字段配合工作的流程是：AI 引擎在某篇文章里看到 `author: {"@id": ".../#person"}` → 沿 `@id` 找到 Person 块 → 读到 `sameAs` 去知乎和 GitHub 验证"纪优"的身份 → 读到 `knowsAbout` 确认这个人在"GEO"领域有专业声明 → 综合 `@id` 的一致性和 `sameAs` 的验证结果，决定这个实体是否可信、是否值得在回答里引用为来源。这个链条里任何一环缺失或错误，AI 拼出的就是一个残缺或矛盾的身份画像。
